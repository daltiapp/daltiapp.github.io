# AK-SCHEDULE-001 · 대회일정 연도별 탐색 및 JSON 분리 설계

- 상태: 제안 / 구현 전 검토
- 작성·자료 확인일: 2026-09-07
- 대상: Flutter 앱, 정적 데이터 저장소, Data Studio, agility-scraper 및 NAS 일정 배치
- 우선순위: A단계 사용성 개선 우선, B단계 파일 분리는 별도 승인 후 진행
- 이번 산출물: 티켓 문서만 작성. 앱·JSON·manifest·NAS·Drive 변경 및 배포 없음.

## 1. 결론

**앱에서는 연도별로 탐색하게 하되, JSON 파일 분리는 두 번째 단계로 진행한다.**

1. **A단계:** 기존 전체 `match.json`을 유지하면서 `예정·진행 중`과 `연도별 전체 일정`을 선택할 수 있게 한다. 지난 대회를 찾을 때 월 이동을 반복하지 않도록 연도를 직접 선택하고, 목록·달력·상세 사이에서 탐색 위치를 유지한다.
2. **B단계:** 동일한 원본에서 연도별 JSON과 인덱스를 생성한다. 새 앱은 필요한 연도 파일만 읽고, 기존 앱·NAS 배치는 계속 전체 `files.match`를 읽는다. 연도별 파일을 각각 수동 편집하지 않는다.
3. **기본 화면은 올해만 제한하지 않는다.** 12월에 접수하는 다음 해 1월 대회와 연말부터 연초까지 이어지는 대회를 놓치지 않는 것이 파일 크기 감소보다 중요하다.

현재 데이터는 73건, 전체 JSON은 63,387 bytes이며 로컬 gzip 결과는 9,115 bytes다. 지금은 대용량 데이터 병목이 확인된 상황이 아니다. 파일 분리로 속도가 크게 좋아진다고 단정하지 않고, 먼저 탐색 편의성을 개선한 뒤 실제 앱 측정으로 분리의 비용 대비 효과를 확인한다.

## 2. 현황과 근거 범위

### 2.1 확인한 데이터

기준 파일: [현재 manifest](../../agilitykorea-manifest.json), [v3 전체 일정](../../ak/v3/match/match.json), [v2 전체 일정](../../ak/v2/match/match.json).

| 시작 연도 | 대회 수 | 연도별 JSON 예상 bytes | 로컬 gzip bytes |
| --- | ---: | ---: | ---: |
| 2024 | 8 | 4,356 | 513 |
| 2025 | 28 | 22,607 | 3,670 |
| 2026 | 37 | 36,478 | 5,992 |
| 기존 전체 파일 | 73 | 63,387 | 9,115 |

측정 방법: Node.js로 현재 v3를 읽고 `startAt`의 연도로 묶은 뒤, 각 그룹을 `{ "competitions": [...] }` 형태로 `JSON.stringify(payload, null, 2) + '\n'` 직렬화하고 `zlib.gzipSync`로 압축했다. 연도 파일은 디스크에 생성하지 않았다. 현재 날짜 표기는 시간대 오프셋 없는 한국 대회 시각이며, 구현에서는 문자열 앞 네 자리만 사용하는 대신 5절의 시간대 규칙을 적용한다.

이 수치는 HTTP 응답의 실제 전송량·지연시간이 아니다. 인덱스 요청, 응답 헤더, 서버 압축 여부, 이미지 전송량도 포함하지 않는다. 2026년 파일만 읽는 경우의 gzip 절감은 약 3.1KB에 불과하므로 추가 네트워크 왕복이 이득을 상쇄할 수 있다.

- v2와 v3 모두 73건이다. 기존 요구대로 대회 내용은 동기화하고, v2에는 이미지가 없어도 된다.
- v3에서 이미지가 있는 대회는 20건, `detailImages` 참조는 207개, 고유 URL은 140개다. 여러 대회가 같은 포스터를 참조할 수 있으므로 참조 수 차이를 중복 대회로 판단하지 않는다.
- 실제 manifest는 `basePath=/ak/v3`, `schemaVersion=2`, `dataVersion=20260907.7`이다.
- [AGENTS.md](../../AGENTS.md)의 활성 경로 설명은 아직 `/ak/v2`다. [현재 데이터 계약](../../AGILITYKOREA_DATA_VERSIONING.md)은 `/ak/v3`로 설명한다. 구현 전 문서 불일치를 해소해야 하며, 오래된 설명에 맞춰 manifest를 되돌리지 않는다.

## 4. 앱 사용성 요구사항 — A단계

### 4.1 사용자 시나리오와 화면 동작

| 사용자 의도 | 권장 동작 | 성공 조건 |
| --- | --- | --- |
| 다음 참가 대회 확인 | 기본 범위는 `예정·진행 중`, 날짜 오름차순 | 올해·다음 해 여부와 관계없이 아직 끝나지 않은 공개 일정이 보인다. |
| 작년 대회·포스터 확인 | 헤더의 범위 선택에서 `2025년 전체` 선택 | 연도를 한 번 선택하면 해당 연도의 종료 대회까지 볼 수 있다. |
| 특정 달 확인 | 연도 선택 후 월 탐색, 목록/달력 전환 | 이전 해까지 월 이동을 여러 번 할 필요가 없고 초점이 유지된다. |
| 상세를 보고 복귀 | 직전 범위·월·선택 날짜·목록 스크롤 복원 | 상세를 닫았다고 올해 또는 오늘로 이동하지 않는다. |
| 다시 현재 일정 확인 | 항상 보이는 `오늘` 동작 | 범위는 `예정·진행 중`, 달력은 오늘, 목록은 가장 가까운 일정으로 이동한다. |

헤더의 범위 선택지는 `예정·진행 중`과 `2026년 전체`, `2025년 전체`, `2024년 전체` 등으로 구성한다. 연도는 고정값이 아니라 데이터로 만든다. 목록/달력 전환은 범위 선택과 독립된 보기 설정이다. 기존 `종료 대회 표시`는 새 범위 선택과 중복되지 않게 대체하며, 숨은 필터가 남아 과거 연도를 빈 화면으로 만들지 않도록 한다.

- 연도 범위는 **그 해에 하루라도 개최되는 대회 전체**다. 접수 연도나 게시 연도가 아니다.
- 연도별 목록도 날짜 오름차순으로 유지하고 월별 구분선을 둔다. 첫 진입 위치는 현재 연도는 오늘 인근, 과거 연도는 마지막 대회가 있는 달, 미래 연도는 첫 대회가 있는 달로 정한다. 사용자가 이동한 뒤에는 해당 위치를 우선한다.
- 여러 연도가 섞이는 예정 목록은 `2026년 12월`, `2027년 1월`처럼 연도를 포함한 구분을 표시한다. 상세에도 연도를 포함한 전체 날짜를 표시한다.
- 달력에서 12월↔1월 이동 시 표시 연도와 선택 범위를 함께 갱신한다. `예정·진행 중` 모드에서는 모드를 유지하고 초점 월만 바꾼다.
- 첫 설치·새 세션 기본은 예정 일정이다. 세션 내 탐색 상태는 유지한다. 기존 `showEnded` 저장값이 있는 업데이트 사용자는 첫 진입 시 현재 연도 전체로 매핑하되, 새 범위가 화면에 명확히 보이게 한다.
- 범위 선택 창은 최신 연도부터 표시한다. 데이터가 없어도 올해 및 현재 초점 연도는 선택 가능하게 하고, 빈 연도도 `오늘`·다른 연도 이동을 막지 않는다.

### 4.2 상태와 이미지

- `로딩 중`, `이 범위에 일정 없음`, `불러오기 실패`, `오프라인 저장본`을 구분한다. 데이터를 못 받은 상태를 대회 0건으로 표시하지 않는다.
- 네트워크 실패 시 마지막 검증된 해당 범위 데이터를 유지하고 저장 시각·재시도를 제공한다. 저장본도 없으면 오류를 표시하되 연도 선택과 오늘 버튼은 남긴다.
- 예정 범위가 여러 연도에 걸쳐 있고 일부 파일이 실패하면 `일부 연도 일정을 불러오지 못했습니다`와 실패 연도 재시도를 표시한다. 부분 결과를 전체 결과처럼 표시하지 않는다.
- 목록 진입만으로 모든 포스터를 다운로드하지 않는다. 기존 상세 이미지 흐름을 유지하고, 상세에서 필요한 이미지를 지연 로딩한다. 이미지 실패가 일정의 날짜·장소·종목 표시를 막지 않게 한다.
- `detailImages`와 기존 Drive `Competitions/대회별 폴더`는 그대로 유지한다. JSON의 연도 분리를 이유로 이미지 이동·재업로드·공개 URL 변경·중복 삭제를 수행하지 않는다.
- TalkBack/VoiceOver에 선택된 연도, 전체 날짜, 예정/종료 상태를 읽어준다. 연도 선택 등 주요 조작은 최소 48×48 논리 픽셀 터치 영역을 확보하고 큰 글자에서도 조작할 수 있게 한다. 상태를 색으로만 구분하지 않는다.

## 5. 날짜·중복·정체성 규칙

1. **시간대:** 이 국내 일정의 기준은 `Asia/Seoul`이다. 기존 오프셋 없는 시각은 한국 시각으로 해석한다. 오프셋 있는 값은 한국 시각으로 변환한 뒤 연도·날짜를 구한다. 기기의 해외 시간대에 따라 대회 소속 연도가 바뀌면 안 된다.
2. **저장 연도:** 한국 시각의 `startAt.year`를 사용한다. `applicationStartAt`, 수집일, 원문 게시일로 나누지 않는다.
3. **표시 구간:** 현재 앱과 같이 대회 마지막 날짜를 포함한다. 날짜 단위 비교에서 조회 구간 `[시작일, 다음 구간 시작일)`과 대회 구간의 겹침은 `eventStartDate < rangeEndExclusive && eventEndDate >= rangeStart`다. RFC 5545의 `DTEND`를 그대로 대입하지 않는다.
4. **연도 경계:** 2026-12-31~2027-01-02 대회는 2026 파일에 한 번만 저장하되, 2026년·2027년 화면 양쪽에 표시한다. 2027 파일만 읽는 구현은 금지한다.
5. **예정 판정:** `eventEndDate >= todayInSeoul`이다. 2026년 12월에 접수하는 2027년 1월 대회는 예정 목록에 노출하고, 접수 상태는 기존 접수 시각 규칙으로 별도 판정한다.
6. **날짜 변경:** 개최일이 다른 연도로 정정되면 같은 생성 작업에서 옛 연도에서 제거하고 새 연도에 추가한다. 이전·새 인덱스의 연도 파일을 혼합하지 않는다.
7. **URL은 단독 고유키가 아니다.** 현재 데이터에는 한 게시물 URL을 공유하는 서로 다른 시간대의 대회가 있다. Instagram→공식 상세 URL 정정도 가능하다. 연도 분리 중 URL 기준으로 합치거나 삭제하지 않는다.
8. **이번 단계에는 레코드 필드를 추가하지 않는다.** 13개 core 필드와 `eventChair`, `detailImages` 선택 필드를 보존한다. 원본 대조에는 전체 레코드의 정규화 비교를 사용하고, 기존 `(name, startAt, url)` 검증키는 영속 ID가 아닌 충돌 검사로만 취급한다.
9. **영속 ID는 후속 의존성이다.** 즐겨찾기·대회별 딥링크·일정 정정 추적을 도입할 때는 URL·날짜와 무관한 ID와 이전 ID 매핑을 별도 설계한다. 이를 현재 엄격한 레코드 계약에 조용히 추가하지 않는다. Data Studio와 감지기의 URL 단독 중복 판별은 연도별 쓰기 경로를 확장하기 전에 같은 URL의 복수 대회를 보존하는 테스트로 보강한다.

## 6. 데이터 구조 비교와 권장안 — B단계

| 방안 | 장점 | 비용·위험 | 결정 |
| --- | --- | --- | --- |

| 연도 JSON + 인덱스 + 호환 전체 JSON | 연도 탐색·부분 로딩과 기존 소비자 공존 | 생성·캐시·검증 경로가 늘어남 | B단계 권장 |

### 6.1 단일 원본과 경로

편집 원본은 기존 전체 일정 한 벌로 유지한다. Data Studio·수집 검수는 그 원본만 갱신하고, 하나의 생성기가 전체 호환본·연도별 파일·인덱스·v2 이미지 제외본을 만든다. 연도 파일을 편집한 뒤 전체본도 따로 고치는 양방향 동기화는 만들지 않는다.

아래는 **승인 후 신규 버전 영역의 제안 구조**다. 실제 경로는 항상 manifest에서 해석한다. 이번 티켓은 `/ak/v4`를 만들거나 전환하지 않는다.

```text
agilitykorea-manifest.json
  files.match      -> match/match.json              # 기존 앱·배치용 전체 일정
  files.matchIndex -> match/index.<indexSha256>.json # 신규 앱의 연도 목록

<manifest.basePath>/
  match/
    match.json
    index.<indexSha256>.json
    years/
      2024.<contentSha256>.json
      2025.<contentSha256>.json
      2026.<contentSha256>.json
  ... 기존 manifest가 참조하는 나머지 JSON 전체
```

`files.matchIndex`도 기존 `files.*`와 같은 상대 경로 **문자열**이다. 객체·배열을 `files.match`에 넣거나 기존 키를 삭제하지 않는다. 연도 파일의 최상위 구조는 기존과 같은 `{ "competitions": [...] }`다.

인덱스의 2026 항목만 보여주는 예시다. `sha256`은 형식을 설명하는 자리표시자이며, 실제 값·건수·날짜 경계는 생성기가 계산한다. 실제 인덱스에는 모든 저장 연도를 포함한다.

```json
{
  "indexVersion": 1,
  "timeZone": "Asia/Seoul",
  "partitionBy": "startAtYear",
  "years": [
    {
      "year": 2026,
      "file": "match/years/2026.<sha256>.json",
      "sha256": "<sha256>",
      "count": 37,
      "minStartDate": "2026-01-24",
      "maxEndDate": "2026-11-22"
    }
  ]
}
```

- `years[].file`는 인덱스 디렉터리 기준이 아니라 **manifest의 basePath 기준**이다. `../`, 절대 URL, 경로 중복 조립을 거부한다.
- `sha256`은 최종 UTF-8 JSON bytes(마지막 개행 포함)의 SHA-256 전체 64자리 소문자 hex다. HTTP 압축 전 원문에 대해 검증한다. 같은 내용은 같은 경로를 재사용한다.
- 연도별 건수·날짜 최소/최대는 수동 입력하지 않는다. 0건 연도는 파일을 만들지 않아도 된다. 화면의 선택 가능 연도는 실제 대회가 걸치는 연도와 올해·현재 초점 연도를 포함한다.
- `count`는 해당 파일에 저장된 건수다. 연도를 걸치는 대회 때문에 화면의 해당 연도 건수와 다를 수 있으므로, 화면 결과 건수는 실제 구간 필터 후 계산한다. 날짜 최소/최대 사이의 모든 날에 대회가 있다는 뜻도 아니다.
- 생성 순서와 필드 출력 순서를 고정하고 한글·2칸 들여쓰기·마지막 개행을 유지한다. 시간별로 달라지는 생성 시각을 연도 파일에 넣어 매번 모든 hash를 바꾸지 않는다.
- 루트 `schemaVersion`은 기존 호환 계약을 깨는 경우에만 올린다. 위 선택적 인덱스 추가와 동일 레코드 유지가 모든 소비자에서 호환됨을 증명하면 2를 유지할 수 있다. `indexVersion=1`은 새 인덱스의 독립 계약이다. 구조 변경 배포는 프로젝트 규칙에 따라 새 `/ak/vN` 전체본에서 준비하며, 후보 `/ak/v4` 활성화는 사용자 명시 승인 사항이다.

### 6.2 조회와 캐시

1. 루트 manifest를 읽는다. 유효한 기존 manifest에 `files.matchIndex`가 없으면 기존 `files.match`를 사용하는 **명시적 호환 모드**다. manifest 오류나 존재하는 인덱스의 파손을 구경로 접근으로 숨기지 않는다.
2. 새 인덱스를 검증한다. 표시 날짜 범위와 `minStartDate`~`maxEndDate`가 겹치는 파일만 고른다. 범위 메타데이터는 후보 파일 선택용이며, 읽은 레코드에 5절의 실제 구간 필터를 다시 적용한다.
3. 예정 목록은 `maxEndDate >= todayInSeoul`인 모든 후보 파일을 읽는다. 올해와 내년 두 개로 하드코딩하지 않는다. 달력 조회는 화면에 보이는 전월·다음 달 날짜 셀까지 범위를 포함한다.
4. 검증된 파일의 캐시는 `service + schemaVersion + resolvedPath + contentHash` 단위로 재사용한다. 공지 `dataVersion`만 변경됐다고 내용이 같은 2024년 파일을 다시 받지 않는다. 인덱스/manifest의 최신성 검사는 계속 수행한다.
5. 기존 Drift·조건부 요청을 활용한다. 같은 파일의 동시 요청을 합치고, 연도를 빠르게 바꿨을 때 늦게 도착한 응답이 현재 선택을 덮어쓰지 않게 한다. 성공한 파일만 완료 처리하고 실패 파일은 재시도 가능하게 유지한다.
6. 각 조회는 하나의 검증된 인덱스에 고정한다. 실패 시 같은 인덱스의 캐시를 사용하거나, 마지막 완전한 이전 조회 결과 전체를 저장본으로 표시한다. 서로 다른 revision의 파일을 섞어 날짜 정정 대회가 두 번 나타나게 하지 않는다.
7. 인덱스에 없는 과거 캐시를 새 데이터처럼 병합하지 않는다. 유효한 마지막 저장본 표시와 최신 조회 결과를 구분한다. 새 인덱스 수신만으로 기존 캐시를 먼저 전부 삭제하지 않는다.

## 7. 호환성·운영·푸시 안전

- **v2/v3 일정 동일성:** 지원 중인 두 전체본은 `detailImages`를 제외한 레코드가 일치해야 한다. 후속 버전 준비 중에도 이 약속을 중단하지 않는다. 이미지 URL은 v3와 연도별 산출물에서 그대로 유지한다.
- **NAS 입력 유지:** 일정 감지·발송 및 Data Studio 규칙 추론은 manifest `files.match`의 전체본을 사용한다. 연도 파일을 순회하며 발송기를 여러 번 실행하는 방식은 금지한다.
- **재생성 ≠ 신규 수집:** 파일 이동·분할·정렬·hash 변경으로 신규 대회 또는 발송 후보를 만들지 않는다. 기존 수집 상태·발송 완료 상태를 보존하며 무조건 초기화하지 않는다.
- **푸시 가드 유지:** 스크립트 하나의 1회 실행에서 발송 대상 대회가 3건 이상이면 FCM을 차단하고 운영자 Telegram 확인만 요청한다. 연도별 소배치로 나눠 우회하면 안 된다. 공지의 게시일 최근 2일 규칙도 변경하지 않는다.
- **검증은 무발송:** 후보 계산은 고정 날짜 fixture와 외부 전송을 막은 테스트에서 수행한다. 마이그레이션 검증을 이유로 운영 FCM·Telegram 실행 명령을 호출하지 않는다.
- **이미지·수집 범위 불변:** agility.co.kr을 일정 확인의 기본 자료로 사용하는 정책, 실제 상세 URL, 기존 심사위원·장소·랭킹전 정보, 승급전 `LV1/LV2/LV3` 및 비/노 `비기너/노비스` 규칙을 보존한다.
- **공지 불변:** 연도 분리 작업이 공지 재수집·수동 수정·활성 queue 재생성을 유발하지 않게 한다. 새 버전 전체 JSON을 준비할 때도 공지는 기존 검증된 산출물을 사용한다.

| AC03 | 복수 세션 | 동일 URL의 오전·오후 대회가 별도 항목으로 유지된다. 제목·URL만으로 중복 제거하지 않는다. |
| AC04 | 접수 연도 경계 | 12월 접수·다음 해 1월 개최 fixture가 예정 목록과 기존 접수 시작/마감 후보 계산에 모두 포함된다. |
| AC05 | 개최 연도 경계 | 12/31~1/2 대회는 한 파일에만 존재하고 두 연도 화면에 나타난다. 통합 예정 목록에는 한 번만 나타난다. |
| AC06 | 시간대·날짜 의미 | 기기 시간대가 한국/UTC/미국이어도 한국 개최일과 연도는 동일. 종료일 당일까지 표시되고 다음 날 제외된다. 윤년 2/29·시간 미상 00:00 기록도 날짜가 밀리지 않는다. |
| AC07 | 날짜 정정·연도 이동 | 2026→2027 정정 후 이전 항목이 잔존하지 않는다. 새 파일 하나가 실패해도 이전·새 revision을 섞지 않는다. |
| AC08 | 탐색 사용성 | 헤더 열기→연도 선택의 2개 조작으로 과거 연도 진입. 목록/달력 전환·상세 복귀 후 범위·초점·스크롤 보존. 오늘 동작은 1회로 현재 범위 복귀. |
| AC09 | 접근성·빈 상태 | 큰 글자에서 연도 선택/오늘 버튼 사용 가능. 스크린리더로 선택 상태·전체 날짜 식별 가능. 빈 연도·오류에서도 범위 변경 가능. |
| AC10 | 네트워크·캐시 | 같은 hash의 연도 재방문은 JSON 본문 재다운로드 0회. 무관한 공지 갱신 시 과거 연도 본문 재다운로드 0회. 다운로드 실패는 0건 일정으로 표시하지 않음. |
| AC11 | 경합·부분 실패 | 빠른 연도 전환 후 최종 선택만 화면에 적용. 복수 연도 중 실패가 있으면 완전한 결과처럼 표시하지 않고 재시도 가능. |
| AC12 | 경로·파손 | 누락 파일, 잘못된 hash·count·날짜 경계·중복 연도·지원하지 않는 indexVersion·경로 탈출을 거부. manifest 실패 시 구경로 접근 0회. |
| AC13 | 기존 소비자 호환 | 유효한 기존 manifest는 전체본 모드로 로드. 인덱스 추가 manifest는 기존 앱과 모든 배치의 실제 파서로 통과. 신규 앱의 롤백된 manifest도 통과. |
| AC14 | 생성 재현성 | 같은 원본을 두 번 생성한 파일 bytes/hash가 동일. 2026년만 수정하면 2024·2025 파일/hash 불변. hash 참조 파일은 덮어쓰지 않는다. |
| AC15 | 푸시 안전 | 같은 고정 날짜·상태에서 분리 전후 후보와 완료 판정 동일. 재생성만 한 fixture의 신규 발송 0건. 서로 다른 연도에 걸친 합산 3건 이상도 FCM 0건. 외부 전송은 mock으로 확인. |
| AC16 | 기존 업무 데이터 | 심사위원·장소·종목·승급전 표기·상세 URL 정정 이력·선택 필드가 분리 전후 동일. 공지 데이터/queue 변경 0건. |

### 측정 계획과 B단계 착수 판단

- A단계 전후 동일한 테스트 기기·빌드 모드·데이터·네트워크 조건에서 첫 유효 일정 표시 시간, 캐시 재방문 시간, 연도 전환 시간, 요청 수·본문 전송량을 기록한다. 이미지 포함/제외 결과를 분리한다.
- 각 조건을 최소 30회 측정해 중앙값과 p95를 남긴다. 최초/캐시 보유/오프라인을 구분하며, 표본이 작은 p95의 한계도 적는다. 이번 문서에는 미측정 성능 수치를 만들지 않는다.
- 사용자 확인 과제는 `다음 대회 찾기`, `작년 특정 대회와 포스터 찾기`, `상세에서 돌아와 탐색 이어가기`다. 우선 대표 사용자 5명으로 발견형 테스트를 하되 모집이 어렵다면 내부 검증임을 구분한다. 소규모 결과를 통계적 효과로 일반화하지 않는다.
- B단계는 과거 아카이브의 독립 갱신 필요성이 생기거나, 실측에서 전체본 전송/파싱 비용이 의미 있게 확인된 후 진행한다. 초기 제안 게이트는 **같은 조건의 p95 첫 표시 시간이 A단계보다 10% 넘게 악화되지 않고 AC10을 만족하는 것**이다. 이는 논문의 기준이 아니라 이 프로젝트의 검토용 기준이다.
- 추가 왕복 때문에 초기 표시가 느려지면 A단계 전체본 로딩을 유지한다. 연도 UI와 파일 분리의 출시를 묶어 사용성 개선을 지연시키지 않는다.

## 10. 전환 및 복구 절차

1. T0~T2로 기존 전체본을 사용하는 A단계를 먼저 검증·출시한다. 데이터 구조나 활성 manifest는 바꾸지 않는다.
2. B단계 승인 후 T3~T5를 수행한다. 인덱스가 없는 현재 manifest와 새 인덱스가 있는 manifest를 모두 읽는 앱을 준비하고, 이전 지원 앱·NAS의 호환 테스트를 통과시킨다.
3. 새 버전 전체 JSON과 내용 해시 기반 연도 파일·인덱스를 비활성 상태로 준비한다. 구조 변경 경로와 `schemaVersion` 결정 근거를 데이터 계약에 기록한다. 기존 `/ak/v2`, `/ak/v3`는 삭제하지 않는다.
4. 정적 호스팅에서는 Git 커밋 한 개가 모든 CDN 응답의 동시 전환을 보장한다고 가정하지 않는다. 참조될 불변 파일을 먼저 배포하고, 공개 URL의 JSON·hash·상대 경로를 확인한 뒤 manifest를 마지막에 전환한다. 이때도 FCM·Telegram은 호출하지 않는다.
5. 전체 호환본은 현재와 같은 가변 경로이므로 신규 인덱스 소비자 수준의 스냅샷 원자성을 보장하지 못한다. NAS는 배포 완료와 계약 검증 후 한 로컬 저장소 revision에서 읽도록 하고, 자동 수집 쓰기와 전환 작업이 겹치지 않게 조정한다.
6. 실제 전환 직전 백업한 manifest 전체와 데이터/스크립트 revision을 기록한다. 장애 시 사용자 승인된 복구 절차로 이전 manifest 전체를 복원하고 이전 버전 폴더를 사용한다. 이전 인덱스·해시 파일은 복구 및 오프라인 재방문을 위해 보존하고 즉시 정리하지 않는다.
7. 전환 후 앱의 예정·과거·이미지 상세, NAS의 읽기 경로, 후보 계산 동등성을 확인한다. 운영 발송 재개는 별도 운영 승인·안전 가드에 따른다. 문제가 없다는 이유만으로 수집/발송 상태를 초기화하지 않는다.

## 11. 범위 밖과 남은 승인

- 신규 API 서버·DB, 월별 분할, 달력 라이브러리 교체, 이미지 재압축·Drive 폴더 재정리는 범위 밖이다.
- 대회 내용 재수집이나 잘못된 URL의 일괄 수정은 별도 데이터 정정 작업이다. 이 티켓의 이관 검증과 섞지 않는다.
- 영속 대회 ID·즐겨찾기·대회별 딥링크는 별도 계약 변경 티켓으로 다룬다.
- **검토 제안:** A단계 구현을 먼저 진행하고, B단계는 측정 결과와 운영 부담을 확인한 후 승인한다. 새 버전 활성화·NAS 변경·실제 커밋/푸시는 이 문서만으로 실행하지 않는다.

## 12. 문서 작성 검증 범위

이 티켓의 수치·코드 근거는 2절의 로컬 snapshot에 한정한다. 외부 참고 자료는 3절의 원문을 확인했으며, 설계 권고는 그 근거와 현행 코드에서 도출한 제안이다. 앱에서 문제를 재현하거나 성능·접근성을 실측한 결과는 아직 없으며, 해당 검증은 하위 작업의 완료 조건으로 남겨 둔다.

저장소의 Karpathy 지침에 따라 단계·가정·성공 조건을 분리하고 운영 데이터 변경을 제외했다. 이 파일은 수동 설계 티켓이며 OpenWiki가 생성하는 저장소 설명이나 Claims를 대체하지 않는다.
